# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Gladiator Dice Game** — a turn-based gladiator roguelite where the player upgrades the faces of a six-sided die instead of leveling a character ("You don't build a hero. You build a die."). Design lives in `Docs/`:

- `Docs/GDD.md` — high concept, design pillars, core loop (Battle → Gold → Market → modify die → next battle), die face structure. Check new mechanics against the pillars (build crafting first, synergies over raw numbers, high risk/high reward).
- `Docs/DevLog.md` — day-by-day log of what was built and why. Each feature so far has been followed by a DevLog entry (`## Day N - Title` with Accomplished / Decisions / Next Steps); the latest "Next Steps" is the current to-do list. Some entries describe designs the code no longer matches (e.g. Day 6 mentions an `ActionEffect.multiplier` that does not exist) — the code is the source of truth.
- `Docs/Roadmap.md` — empty for now.

Code, comments, docs and commit messages are in English. Commits use Conventional Commit style (`feat: ...`).

## Environment

- Unity **6000.4.0f1** (Unity 6), URP 2D, new Input System, uGUI + TextMesh Pro.
- No assembly definitions: all scripts compile into `Assembly-CSharp`. No tests exist yet (Unity Test Framework is installed but unused).
- There is no CLI build/test setup. Code is compiled and run from the Unity Editor. Scenes: `Assets/Scenes/RunStart.unity` (first in Build Settings), `Battle.unity` and `Market.unity`, all loaded by name from `RunManager`.
- Testing in Play Mode through MCP: `PlayerSettings.runInBackground` is off, so when the Editor is not the focused window Play Mode stops advancing frames. Code invoked directly still runs, but `Start()` of a freshly loaded scene does not until the user focuses the Editor.
- The Editor is reachable through **MCP for Unity** (`com.coplaydev.unity-mcp`, pinned in `Packages/manifest.json`; set up via `Window → MCP for Unity`). Its tools only work while the Editor is open with the bridge running. Use them to read the Console after script changes and to inspect the scene; without them, ask the user to paste compile errors.
- When creating or moving files under `Assets/`, Unity generates `.meta` files on import. Never hand-write or delete `.meta` files without their asset; moving a script must move its `.meta` too, or scene/asset references break.

## Architecture (`Assets/Scripts`)

### Run (survives scene loads)
- `RunData` — plain `[Serializable]` C# class with everything that lives for a whole run: the player's die (`dieFaces`, a `List<DieFace>`), `maxHP`/`currentHP` (HP carries over between battles), `gold`, `battlesWon`, `equipment`. Keep it free of Unity objects other than asset references so it can be saved as JSON later.
- `RunManager` — singleton MonoBehaviour that owns `RunData`, calls `DontDestroyOnLoad` and handles scene flow (`GoToMarket`, `GoToNextBattle`, `RestartRun`). It is never placed in a scene: a `[RuntimeInitializeOnLoadMethod(BeforeSceneLoad)]` bootstrap instantiates `Assets/Resources/RunManager.prefab`, so every scene can be played directly. The starting die (5 faces: 2 Sword, 2 Shield, Health Potion) and starting HP are configured on that prefab, which also references the economy and encounter configs.
- Run start: `StartNewRun` fills `RunData.startingFaceOffers` via `StartingFaceOffers.Generate` (Market pool minus starter faces, starting rarity weights from `EconomyConfigSO`, offers never share a tag). `RunStartUI` (RunStart scene) shows them and calls `ChooseStartingFace`, which adds the sixth face. `RestartRun` loads RunStart. If the Battle scene starts without a chosen starting face (e.g. Play pressed with Battle open in the Editor), `BattleManager.Awake` disables itself and sends the player to RunStart, so the choice is never skipped.
- `EconomyConfigSO` (`Assets/Config/EconomyConfig.asset`) — every economy number (gold per victory, buy price per rarity, upgrade multiplier per rarity) and the `GetBuyPrice` / `GetUpgradeCost` formulas from the GDD's "Rarity & Economy" section.
- Dependency direction: the battle borrows the die and HP from the run in `BattleManager.Awake` and reports the result through `RunManager.OnBattleEnded`. The run decides what happens next; battle code knows nothing about the market.
- `RunManager.bossBattles` (currently 4 and 8) marks boss slots; `IsGrandMarket` is true right after winning one, and winning one heals `bossHealFraction` (50%) of max HP and pays `EconomyConfigSO.bossVictoryBonus` (30 gold) on top of `goldPerVictory`. Boss enemies and the final boss are not implemented yet. Prefab values (starting HP 50, heal fraction, references) override the defaults in code.
- Market is split into model and view:
  - `Market` — plain C# rules, no UI: generates offers from `EconomyConfigSO.marketPool` (Normal: rarity weights 70/25/5, tag-match chance; Grand: Epic only; a face is offered at most once per visit, so the Grand Market shows fewer offers if the pool has fewer Epics), `Buy(offer, dieSlot)` replaces a die face with a new `DieFace`, `Upgrade(dieSlot)` raises an instance's value, `Reroll()` pays `GetRerollCost()` (rising within the visit, see `EconomyConfigSO.GetRerollCost`; Grand Market costs more) for a fresh set of offers (faces and modules) that avoids the replaced ones when possible. The Normal Market also offers `modulesPerMarket` (2) action modules from `EconomyConfigSO.modulePool` with the same rarity/tag rules (`moduleOffers`, `CanBuyModule`, `CanAttachModule`, `BuyModule(offer, dieSlot)`); the Grand Market sells none. Equipment: the Grand Market sells `equipmentPerGrandMarket` (2) items from `EconomyConfigSO.equipmentPool` (`equipmentOffers`, `BuyEquipment(offer, replaceSlot)`), and when `RunData.bossRewardPending` is set (by a boss victory in `RunManager.OnBattleEnded`) the Market also generates `rewardChoices` (`ClaimReward(choice, replaceSlot)`, `SkipReward`). `replaceSlot` -1 means a free slot; owned items are never offered. Upgrade rule: Normal Market upgrades Common/Rare, Grand Market upgrades Epic. Test new rules on `Market` directly, without a scene.
  - `MarketUI` — draws the `Market` state and forwards clicks. `OfferCardUI` / `DieSlotUI` only hold references to the scene objects; `OfferCardUI.DescribeFace` is the shared face card text (Market and RunStart), `DescribeModule` / `DescribeEquipment` the module and item card text. The second card row (`extraCards`) shows modules in the Normal Market and equipment in the Grand Market; `EquipmentSlotUI`s show the items and are clickable only while choosing which item to replace; the boss reward panel (`rewardPanel`) covers the screen until the reward is taken or skipped, and Next Battle stays locked until then. Buying is two clicks: an offer, then a die slot; for a module only slots where `CanAttachModule` is true are interactable. Their buttons are wired in `MarketUI.Start` with `AddListener` because each needs its own index; Next Battle is wired in the Inspector.

### Battle state machine
- `BattleManager` (MonoBehaviour in the Battle scene) owns the current `BattleState`, the player and enemy `Entity`, the enemy's `EnemyBrain`, `currentDiceFaces` (a reference to the run's `List<DieFace>`, not serialized) and the `currentRolledFace` (`DieFace`) shared between states.
- `States/` contain plain C# classes (not MonoBehaviours) deriving from `BattleState` (`Enter`/`Execute`/`Exit`), constructed with the manager: `new PlayerRollState(battleManager)`.
- Turn steps live in `BattleFlow` (plain C#, created in `BattleManager.Awake` as `flow`): `StartBattle`, `StartPlayerTurn` (player `OnTurnStart`, TurnStart items, enemy picks its intent), `Roll`, `PlayAction` (ActionChosen items, then the rolled face's effects), `EndPlayerTurn` (TurnEnd items, player `OnTurnEnd`), `EnemyAct`, `EndEnemyTurn`, `WinBattle`. The states and `RunSimulator` both call these, so rule changes go into `BattleFlow`, not into a state or the simulator.
- Turn flow: `PlayerRollState` (`StartPlayerTurn`, shows the intent, waits for roll, `Roll`) → `PlayerActionSelectState` (waits for an action, `PlayAction`, `EndPlayerTurn`) → `EnemyTurnState` (`EnemyAct`, `EndEnemyTurn`) → back to `PlayerRollState`. `BattleOverState` calls `WinBattle` on a victory before reporting the HP to the run.
- `BattleManager.CheckBattleOver()` runs after every action and every `OnTurnEnd`; when a side is dead it switches to `BattleOverState`, and the caller must `return` immediately. `BattleOverState` reports to `RunManager`, shows the result panel, and on the result button goes to the Market (victory) or restarts the run (defeat).
- Input is event-driven: UI buttons call `BattleManager.OnRolled()`, `BattleManager.OnActionSelected(int)` and `BattleManager.OnResultButton()`, which forward only if the current state is the right type. The int is cast to `ActionType` (0 Attack, 1 Defense, 2 Magic), so button wiring depends on enum order.

### Data-driven effects (ScriptableObjects)
- `DieFaceSO` — the definition of a face: `faceName`, `description`, `rarity` (`Rarity`), `tags` (`FaceTag`), `baseValue` (starting value of a new copy), `softCap` (renamed from `maxValue` with `[FormerlySerializedAs]`; upgrades past it are allowed but cost `aboveSoftCapFactor` (2) times more per level, see `EconomyConfigSO.GetUpgradeCost`), and a list of `ActionEffect { ActionType, EffectSO }`. A face can respond to several actions; choosing an action runs every effect tagged with it.
- `DieFace` — an instance on the die: `definition` + its own `value` + its attached `modules`. Effects use the instance's `value`, and upgrades change only the instance. Never modify a `DieFaceSO` at runtime: two copies on the die share one asset. Always read a face's effects through `DieFace.GetEffects(action)` / `HasAction` (definition effects plus module effects), never `definition.effects` directly; show it with `DisplayName` / `FullDescription`.
- `ActionModuleSO` (`Assets/Modules/`) — a bought action (`action`, `effects`, `rarity`, `tags`) attached to an empty action slot of a `DieFace` (`CanAttach`: the face has no effect for that action yet). Its effects use the host face's value. Modules can't be removed; replacing the face discards them.
- Rarity follows value scaling (Common linear, Rare conditional/multi-effect, Epic multiplicative). Current soft cap rule: Common base+3, Rare base+2, Epic base+1. Design rule: the printed value is exactly what the effects use — no per-effect multipliers (removed on purpose, see DevLog Day 9).
- ScriptableObjects are for design data only. Never store mutable run state in an SO asset: changes made in Play Mode persist in the Editor but not in builds.
- `Effects/EffectSO` — abstract strategy: `Execute(EffectContext context)`. `EffectContext` carries `source`, `target`, `value`, `die` (the source's `List<DieFace>`) and `face` (the triggering `DieFace`). `die` and `face` are null for enemy intents, so effects that read them need a fallback. New information for effects goes into `EffectContext` instead of changing the signature. Every damage effect must hit through `context.Hit(amount)` (adds the source's Rage per hit) and every status applied to the opponent must go through `context.ApplyToTarget(status, amount)` (adds the source's Ritual); self-applied statuses and multiplying an existing status (Fuel) bypass Ritual on purpose. Every effect is source/target-agnostic so the same asset works for the player's die faces and for `EnemyIntent`s. Effects must not reach the die through globals such as `RunManager`.
- `EffectSO.Describe(EffectContext)` returns short player-facing text with the real numbers (Rage, Ritual and current stacks included when the context has a source/target), e.g. "5 damage, 4 Bleed". `EnemyBrain.DescribeCurrentIntent` and the action button previews are built from it, so every new effect should override it.
- `IgniteEffectSO` deals damage equal to the target's Burn without consuming it. `StatusStacksDamageEffectSO` deals damage from a status's stacks without consuming them (target's or own; `addValue` on: value + stacks, e.g. Lacerate; off: stacks, at least value, e.g. Spiked Shield).
- `ConditionalEffectSO` runs its inner effects only if a status is present on the target (or on the source with `checkTarget` off), e.g. "if the enemy is bleeding, hit again". Use it for new "if X" faces instead of writing a new effect class. `ConsumeStatusMultiplyDamageEffectSO` is the multiplicative consume (value × stacks, e.g. Exsanguinate); `ConsumeStatusDamageEffectSO` is the additive one (value + stacks, Detonate).
- `ApplyStatusEffectSO.fixedAmount` (> 0) applies a fixed amount instead of the value (Sword's 1 Bleed).
- `ApplyStatusPerTaggedFaceEffectSO` implements die-composition scaling (value × faces on the die with a tag, e.g. Plague); without a die it counts as 1. New mechanics are added as a new `EffectSO` subclass with `[CreateAssetMenu(menuName = "Dice/Effects/...")]`, not by branching in the states.
- Effect assets and face assets are created in the Editor (`Assets/Faces/` holds the faces). `value` meaning is per effect (e.g. `MultiplyStatusEffectSO` treats it as a multiplier).

### Equipment
- `EquipmentSO` (see GDD "Equipment"): name, rarity, tags and `TriggeredEffect`s (`TriggerType`, optional face-tag / action condition, `EffectSO` list, fixed `value`). `RunData.equipment` holds up to `RunData.EquipmentSlots` (3). Items reuse the normal effect assets; conditions on the battle state use `ConditionalEffectSO`.
- `TriggerSystem` (owned by `BattleFlow`) runs the items. Hits come from `Entity.HitDealt` (raised on the attacker for each hit) and `Entity.HitTaken` (a hit that cost HP; ticks and `PayHP` don't count); every other trigger is fired by a `BattleFlow` step. Effects run by a trigger never fire triggers (no chains). `maxPerRound` / `maxPerBattle` (0 = no limit) cap how often a reaction fires; the limit counts firings even when an inner `ConditionalEffectSO` then does nothing. `TriggerType` is serialized as a number: append only.

### Entities and statuses
- `Entity` holds HP, block and a `Dictionary<StatusType, int>` of statuses (`StatusType` enum is in `Entity.cs`). `TakeDamage` is absorbed by Block first, then Fortify (a status that never resets at turn start), then HP. Damage over time uses `LoseHP` and bypasses both; `PayHP` is the public version for HP costs (e.g. Bloodrage), which can kill the player and is then caught by `CheckBattleOver`. Every state change must raise `OnHealthChanged`, which is how `UIManager` refreshes.
- Block resets at the start of the owner's own turn (`OnTurnStart`), not the end.
- Status rules are hardcoded in `Entity`: Burn deals **no** damage on its own (it is fuel for ignitions and Detonate) and decays by 2 at `OnTurnEnd` unless Burn was added since the last tick; Poison deals its stacks at `OnTurnEnd`, bypassing block, then halves (rounded down); Bleed deals 1 at `OnTurnEnd` and loses 1 stack (stacks are duration); Rage and Ritual are permanent for the battle and are applied by `EffectContext`, not by `Entity`; FireShield applies Burn to the attacker when hit (only if `TakeDamage` gets a `source`) and is cleared at turn start. Effects that should trigger FireShield must pass `source` to `TakeDamage`.
- Adding a status means touching `StatusType`, `Entity` turn hooks and `UIManager.BuildStatusText` (which lists statuses explicitly).
- Enums used in assets (`StatusType`, `FaceTag`, `Rarity`, `ActionType`) are serialized as numbers: only add new values at the end, never insert or reorder.

### UI
- All canvases use Scale With Screen Size with a 2560x1440 reference (layouts are authored in that space).
- `UIManager` is a Battle-scene singleton (`UIManager.Instance`, cleared in `OnDestroy`); states null-check it before calling `ShowRollPhase` / `ShowRolledFace` / `UpdateEnemyIntentText` / `ShowBattleResult`. It drives `CombatantPanelUI` (name, HP bar, Block/Fortify, status chips), the intent box, the rolled face panel, the `DieChipUI` strip, the `EquipmentChipUI` strip under the player panel (filled by `ShowEquipment`; `BattleManager.Start` subscribes `FlashEquipment` to `TriggerSystem.ItemTriggered` before `StartBattle`, so every item flashes when it fires) and the action buttons, which preview each action from `EffectSO.Describe` and are disabled when the rolled face has no effect for that action. References are assigned in the Inspector.
- `UI/GameText` is the single source of keyword colors (`Colorize`) and keyword definitions (`Glossary`) for tooltips. Add new statuses/keywords there.
- Tooltips: one `TooltipUI` per scene, shown by `TooltipTrigger` components (the trigger object needs a raycast-target Graphic, e.g. a transparent Image).
- Use `ToUpperInvariant`/`ToLowerInvariant` for UI text: on a Turkish system `ToUpper()` turns "i" into "İ".

### Enemy
- Normal enemies are `EnemySO` assets in `Assets/Enemies/` (name, `EnemyTier` Weak/Medium/Strong, HP, `escalationPerTurn`, intents). `EncounterConfigSO` (`Assets/Config/EncounterConfig.asset`) lists every enemy; the battle scene has a single generic Enemy object whose `Entity` stats and `EnemyBrain` are set from the picked `EnemySO` in `BattleManager.Awake`.
- `EnemyIntent { intentName, intentType, effects, value, weight }`: all effects run with the same value. `EnemyBrain.Setup(enemySO, self, opponent)` stores both entities; it picks intents by weight at the start of the player's turn (the same intent at most 2 times in a row), shows them via `DescribeCurrentIntent`, and runs them in `EnemyTurnState` through `ExecuteCurrentIntent()` (with no `die`/`face` in the context).
- Escalation uses the shared, visible Rage status: intents like Battle Cry or Roar use `GainRageSelfEffect`. `EnemySO.escalationPerTurn` (Rage gained in `EnemyBrain.OnTurnEnd()`) still works but no enemy uses it (Essedarius's made slow builds unwinnable, DevLog Day 33). There is no hidden enemy attack bonus anymore.
- Balance experiments: `RunSimulator.WithFaceValueChanges(deltas, measure)` changes faces' value/soft cap in memory and always restores them; `ClearRates(bots, runs)` and `BotsMatching(...)` keep experiment code short (the MCP `execute_code` compiler is C# 6, so avoid generic inference tricks). Reports include gold entering the first Grand Market and the average die at battle 8. For deeper diagnosis set `RunSimulator.Stats = new RunSimulator.FightStats()` (optionally its `statsTier`), run `Simulate`, read `Stats.Report()` (damage per player turn from actions vs. ticks, HP taken, Bleed uptime, damage per roll for each face) and set it back to null.
- Balance is tuned with `Assets/Editor/RunSimulator.cs` (menu `Tools → Gladiator Dice → Run Balance Simulation`, or call `RunSimulator.DefaultReport(runs, hpScale, damageScale)` from MCP `execute_code`). It simulates full runs with the real `Entity`/`EnemyBrain`/effects/`Market` and twelve bots (no shopping, unplanned, one focused bot per archetype tag, and hybrid bots with several tags: Ritual + Poison, Ritual + Bleed, Block + Rage, Bleed + Rage; `ChooseAction` has face-specific rules that new faces may need), without scenes. Focused bots reroll the Market when nothing fits and they keep at least `GoldToKeepAfterReroll` (40) gold, and spend gold left after upgrades on modules of their archetype, attached to faces outside it (`BuyModules` switches this off for comparisons; `PlayModules` off buys them but never plays them, to separate their gold cost from their use). Modules are niche combo tools for high-value faces, so judge them with combo tests rather than average clear rates. They also take the boss reward and buy equipment they want (`Bot.Want`: archetype 2, general 1, other 0; `UseEquipment` switches it off). Its fights use the same `BattleFlow` steps as the states; its reward rules mirror `RunManager.OnBattleEnded`, so keep those in sync when they change. Scale arguments only affect simulation copies of the enemies.
- `RunManager.PickEnemyForNextBattle` picks by tier (`GetTierForBattle`: Weak before the first boss slot, Medium from it, Strong from the second; boss slots use the next tier until bosses exist) and never repeats an enemy within a run (`RunData.metEnemies`).
