# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Gladiator Dice Game** — a turn-based gladiator roguelite where the player upgrades the faces of a six-sided die instead of leveling a character ("You don't build a hero. You build a die."). Design lives in `Docs/`:

- `Docs/GDD.md` — high concept, design pillars, core loop (Battle → Gold → Market → modify die → next battle), die face structure. Check new mechanics against the pillars (build crafting first, synergies over raw numbers, high risk/high reward).
- `Docs/DevLog.md` — day-by-day log of what was built and why. Each feature so far has been followed by a DevLog entry (`## Day N - Title` with Accomplished / Decisions / Next Steps); the latest "Next Steps" is the current to-do list. Some entries describe designs the code no longer matches (e.g. Day 6 mentions an `ActionEffect.multiplier` that does not exist) — the code is the source of truth.
- `Docs/Roadmap.md` — the big steps after the core game (battle depth, map, multiple enemies, heroes and meta progression), in order, from the user's play-tests.

Code, comments, docs and commit messages are in English. Commits use Conventional Commit style (`feat: ...`).

## Environment

- Unity **6000.4.0f1** (Unity 6), URP 2D, new Input System, uGUI + TextMesh Pro.
- No assembly definitions: all scripts compile into `Assembly-CSharp`. No tests exist yet (Unity Test Framework is installed but unused).
- There is no CLI build/test setup. Code is compiled and run from the Unity Editor. Scenes: `Assets/Scenes/RunStart.unity` (first in Build Settings), `Battle.unity` and `Market.unity`, all loaded by name from `RunManager`.
- Testing in Play Mode through MCP: `PlayerSettings.runInBackground` is off, so when the Editor is not the focused window Play Mode stops advancing frames. Code invoked directly still runs, but `Start()` of a freshly loaded scene does not until the user focuses the Editor.
- The Editor is reachable through **MCP for Unity** (`com.coplaydev.unity-mcp`, pinned in `Packages/manifest.json`; set up via `Window → MCP for Unity`). Its tools only work while the Editor is open with the bridge running. Use them to read the Console after script changes and to inspect the scene; without them, ask the user to paste compile errors.
- When creating or moving files under `Assets/`, Unity generates `.meta` files on import. Never hand-write or delete `.meta` files without their asset; moving a script must move its `.meta` too, or scene/asset references break.

## Architecture (`Assets/Scripts`)

### Run (survives scene loads)
- `RunData` — plain `[Serializable]` C# class with everything that lives for a whole run: the player's die (`dieFaces`, a `List<DieFace>`), `maxHP`/`currentHP` (HP carries over between battles), `gold`, `battlesWon`, `equipment`, `rerollsPerBattle` (2). Keep it free of Unity objects other than asset references so it can be saved as JSON later.
- `RunManager` — singleton MonoBehaviour that owns `RunData`, calls `DontDestroyOnLoad` and handles scene flow (`GoToMarket`, `GoToNextBattle`, `RestartRun`). It is never placed in a scene: a `[RuntimeInitializeOnLoadMethod(BeforeSceneLoad)]` bootstrap instantiates `Assets/Resources/RunManager.prefab`, so every scene can be played directly. The starting die (5 faces: 2 Sword, 2 Shield, Health Potion) and starting HP are configured on that prefab, which also references the economy and encounter configs.
- Run start: `StartNewRun` gives `EconomyConfigSO.startingGold` (20) and fills `RunData.startingFaceOffers` via `StartingFaceOffers.Generate` (Market pool minus starter faces, starting rarity weights from `EconomyConfigSO`, offers never share a tag, `avoid` skips faces already shown). `RunStartUI` (RunStart scene) shows them, rerolls them for gold (`RunManager.RerollStartingFaces` → `StartingFaceOffers.Reroll`, the Normal Market's rising price counted by `RunData.startingOfferRerolls`; the simulator's focused bots reroll up to twice when no offer fits, `RunSimulator.UseStartingReroll`) and calls `ChooseStartingFace`, which adds the sixth face. `RestartRun` loads RunStart. If the Battle scene starts without a chosen starting face (e.g. Play pressed with Battle open in the Editor), `BattleManager.Awake` disables itself and sends the player to RunStart, so the choice is never skipped.
- `EconomyConfigSO` (`Assets/Config/EconomyConfig.asset`) — every economy number (gold per victory, buy price per rarity, upgrade multiplier per rarity) and the `GetBuyPrice` / `GetUpgradeCost` formulas from the GDD's "Rarity & Economy" section.
- Dependency direction: the battle borrows the die and HP from the run in `BattleManager.Awake` and reports the result through `RunManager.OnBattleEnded`. The run decides what happens next; battle code knows nothing about the market.
- `RunManager.bossBattles` (currently 4 and 8) marks the Grand Market slots and `finalBattle` (11) ends the run (`IsRunComplete`; the result panel shows RUN COMPLETE and New Run). `IsGrandMarket` is true right after winning a boss slot, and winning one heals `bossHealFraction` (30%) of max HP and pays `EconomyConfigSO.bossVictoryBonus` (30 gold) on top of `goldPerVictory`. Bosses: `EncounterConfigSO.bossSlots` lists `BossSlot { battle, bosses }`; `RunManager.PickBossForNextBattle` returns the slot's boss or null (a slot without a boss keeps using normal enemies of the next tier). All three exist: the Minotaur (battle 4), Medusa (battle 8) and the Hydra (battle 11, the final boss). Prefab values (starting HP 50, heal fraction, references) override the defaults in code.
- Market is split into model and view:
  - `Market` — plain C# rules, no UI: generates offers from `EconomyConfigSO.marketPool` (Normal: rarity weights 70/25/5, tag-match chance; Grand: Epic only; a face is offered at most once per visit, so the Grand Market shows fewer offers if the pool has fewer Epics), `Buy(offer, dieSlot)` replaces a die face with a new `DieFace`, `Upgrade(dieSlot)` raises an instance's value, `Reroll()` pays `GetRerollCost()` (rising within the visit, see `EconomyConfigSO.GetRerollCost`; Grand Market costs more) for a fresh set of offers (faces, enchantments and items) that avoids the replaced ones when possible. Every Market also has the Enchanting Table: `enchantmentsPerMarket` (3) enchantments from `EconomyConfigSO.enchantmentPool`, generated exactly like face offers (Normal: rarity weights; Grand: Epic only) (`enchantmentOffers`, `CanBuyEnchantment`, `CanEnchant`, `BuyEnchantment(offer, dieSlot)`). Equipment: the Grand Market sells `equipmentPerGrandMarket` (2) items from `EconomyConfigSO.equipmentPool` (`equipmentOffers`, `BuyEquipment(offer, replaceSlot)`), and when `RunData.bossRewardPending` is set (by a boss victory in `RunManager.OnBattleEnded`) the Market also generates `rewardChoices` (`ClaimReward(choice, replaceSlot)`, `SkipReward`). `replaceSlot` -1 means a free slot; owned items are never offered. Locks: `ToggleFaceLock` / `ToggleEnchantmentLock` / `ToggleEquipmentLock` (cost `EconomyConfigSO.lockCost` 2 / `grandLockCost` 5, unlock free) keep an offer through `Reroll` and store it in `RunData.lockedFaces` / `lockedEnchantments` / `lockedEquipment`, which the next Market places first. Upgrade rule: Normal Market upgrades Common/Rare, Grand Market upgrades every face. Healer: `Heal()` / `CanHeal()` / `GetHealCost()` (`EconomyConfigSO.healAmount` 10 for `GetHealCost` 20 gold, `maxHealsPerVisit` 1; `MarketUI.healButton`); bots heal below `RunSimulator.HealBelowFraction` (half HP) when `UseHealer` is on. Test new rules on `Market` directly, without a scene.
  - `MarketUI` — draws the `Market` state and forwards clicks. `OfferCardUI` / `DieSlotUI` only hold references to the scene objects; `OfferCardUI.DescribeFace` is the shared face card text (Market and RunStart), `DescribeEnchantment` / `DescribeEquipment` the enchantment and item card text. The card row (`CardRow`, a layout group) has three sections: faces, the Enchanting Table (`enchantmentCards`) and equipment (`equipmentSection` / `equipmentCards`, Grand Market only, hidden otherwise so the row re-centers); `EquipmentSlotUI`s show the items and are clickable only while choosing which item to replace; the boss reward panel (`rewardPanel`) covers the screen until the reward is taken or skipped, and Next Battle stays locked until then. Buying is two clicks: an offer, then a die slot (with nothing being bought, clicking a die slot picks it to swap); for an enchantment only faces with an empty Magic action are interactable. Their buttons are wired in `MarketUI.Start` with `AddListener` because each needs its own index; Next Battle is wired in the Inspector.

### Battle state machine
- `BattleManager` (MonoBehaviour in the Battle scene) owns the current `BattleState`, the player `Entity` and the scene's enemy `Entity` (which takes the picked enemy's or boss's stats), `currentDiceFaces` (a reference to the run's `List<DieFace>`, not serialized) and the `currentRolledFace` (`DieFace`) shared between states.
- `States/` contain plain C# classes (not MonoBehaviours) deriving from `BattleState` (`Enter`/`Execute`/`Exit`), constructed with the manager: `new PlayerRollState(battleManager)`.
- Turn steps live in `BattleFlow` (plain C#, created in `BattleManager.Awake` as `flow`): `StartBattle`, `StartPlayerTurn` (player `OnTurnStart`, TurnStart items, every living enemy picks its intent), `Roll`, `PlayAction` (ActionChosen items, enemy traits, then the rolled face's effects on the target), `EndPlayerTurn` (TurnEnd items, player `OnTurnEnd`), `EnemyAct` / `EndEnemyTurn` (every living enemy in turn order), `WinBattle`. The states and `RunSimulator` both call these, so rule changes go into `BattleFlow`, not into a state or the simulator.
- Multiple enemies (see GDD "Multiple Enemies"): `BattleFlow.enemies` is a `List<BattleEnemy>` (`entity`, `brain`, its own `traits`), in turn order; dead ones stay in the list and are skipped. `BattleFlow.Target` is the enemy the player's attacks, statuses and items hit (`SelectTarget`; defaults to and falls back to the front living enemy). `IsOver` is true when the player or every enemy is dead. `IncomingDamage` / `ThreatAgainst` sum the living enemies (bots use these, never one brain). Area effects read `EffectContext.opponents` / `AllOpponents` (every living opponent; null means only the target): `ForEachOpponentEffectSO` runs its inner effects once per living opponent with `context.target` swapped (so Rage, Ritual and hit triggers apply per enemy; Cleave, Wildfire, Sweep, Censer), `SpreadStatusEffectSO` copies the target's stacks to the others (Contagion), and `OverkillDamageEffectSO` carries a killing hit's excess to the next living enemy through `TakeDamage` (Follow Through; the excess already holds Rage). See GDD "Area Effects". The single-enemy `BattleFlow(player, enemy, brain, ...)` constructor wraps one `BattleEnemy`. A `BattleEnemy` with `endsBattleOnDeath` (every boss) ends the battle when it dies. Enemies can join mid-battle through `BattleFlow.SpawnEnemy` (needs the constructor's `entityFactory`: a copy of the scene's enemy object in battle, a hidden object in the simulator); `EnemyAdded` lets the UI add a card (`UIManager.AddEnemyCard`, which shrinks all cards past 3). `EnemyAct` / `EndEnemyTurn` loop by index because the list can grow, and an enemy without an intent (`EnemyBrain.HasIntent`) doesn't act. `Entity.Heal` does nothing to a dead entity. The simulator's bots focus the living enemy with the lowest HP (`ChooseTarget`).
- Rerolls (see GDD "Rerolls"): `RerollPool` (owned by `BattleFlow`, refilled every battle from `RunData.rerollsPerBattle`; `Left`, `UsedThisTurn`, `UsedThisBattle`, passed to effects as `context.rerolls`). `BattleFlow.CanReroll` / `RerollFace()` reroll the landed face (not a new turn; FaceRolled items fire again); the Reroll button calls `BattleManager.OnRerollClicked` → `PlayerActionSelectState.Reroll`. Bots reroll with `RunSimulator.ShouldReroll` (`UseRerolls` switches it off). Reroll content uses `GainRerollEffectSO` (`fixedAmount`), `RerollScaledDamageEffectSO` (`RerollsLeft` / `UsedThisBattle` multiplied / `UsedThisBattleAdded`, `perReroll` bonus for the added ones, 2 on Patient Blade and Gambit), `RerollScaledBlockEffectSO` (Hedge: value + rerolls left) and `IfRerolledEffectSO` (inner effects if the source rerolled this turn); the faces carry `FaceTag.Fortune`.
- Die layout (see GDD "Die Layout"): the order of `RunData.dieFaces` is the position on a sideways cross net (`DieLayout`: 0 Top, 1 Left, 2 Middle, 3 Right, 4 Rightmost, 5 Bottom; `OppositeOf`, `NeighborsOf`, `Name`, `Describe`). So never reorder or sort `dieFaces`. `Market.SwapFaces` swaps two places for free (`MarketUI.pendingSwap`: click a face, then another). The Market's die slots and the battle's `DieChipUI`s are placed on the net in their scenes, in index order.
- Roll steering (Fortune's engines, GDD "Rerolls"): `SteerRollEffectSO` (`RollSteer`: `AnyOther` = Change, `Opposite` = Flip, `Neighbor` / `Position` = Tumble, `Chosen`) sets `context.steer`; after the action's effects `BattleFlow.ApplySteer` decides the next roll (`steerTo` or `changeFrom`) and sets `RollsAgainAtOnce` (`BattleManager.RollAgainAtOnce` rolls at once), or `ChoicePending` (`PlayerChooseFaceState` waits for a click on a `DieChipUI`, then `ChooseNextFace`; bots take `StrongestAttacker`). A chain ends at `MaxActionsPerTurn` (3, `ActionsThisTurn`), which also limits Steady Hand; Consumable Change doesn't count as an action. Payoffs use `RollConditionEffectSO` (`FirstTurn`, `LandedTimesThisTurn`, `ArrivedBySteer`, `OppositeHasTag`), fed by `context.faceLandings` / `arrivedBySteer` / `turnNumber`. During a turn, a condition already met previews as just its result. Every face that acted this turn spends its Charge at the turn's end (`actedThisTurn`), unless its action kept it (`keptChargeThisTurn`), not just the last one.
- Consumable and Change (see GDD "Consumable and Change"): `DieFaceSO.consumableActions` lists actions usable once per battle (`IsConsumable`); `BattleFlow.consumables` (`Consumables`, battle-only) records used ones per face instance after their effects run. A used Consumable action is Change (`BattleFlow.IsChange`): `PlayAction` then only counts `ChangesThisTurn` (at most `MaxChangesPerTurn`, 1, enforced by `CanAct`), remembers the face so the next `Roll` lands on any other face, sets `RollsAgainAtOnce` / `RerollPending` and returns, so no items, traits, threat bookkeeping or reroll costs apply; `PlayerActionSelectState` rolls again at once, and the simulator loops like Steady Hand. A stone face is never Change. `BattleFlow.PassTurn` (the Pass button, `BattleManager.OnPassClicked` → `PlayerActionSelectState.Pass`) ends the turn without an action; `EndPlayerTurn` then treats the rolled face as unused (it keeps its Charge). The simulator passes when the face can't act. The UI previews it as "Change: roll another face", marks Consumable actions, and `DieChipUI` shows "used: Change".
- Turn flow: `PlayerRollState` (`StartPlayerTurn`, shows the intent, waits for roll, `Roll`) → `PlayerActionSelectState` (waits for an action, `PlayAction`, `EndPlayerTurn`) → `EnemyTurnState` (`EnemyAct`, `EndEnemyTurn`) → back to `PlayerRollState`. `BattleOverState` calls `WinBattle` on a victory before reporting the HP to the run.
- `BattleManager.CheckBattleOver()` runs after every action and every `OnTurnEnd`; when a side is dead it switches to `BattleOverState`, and the caller must `return` immediately. `BattleOverState` reports to `RunManager`, shows the result panel, and on the result button goes to the Market (victory) or restarts the run (defeat).
- Input is event-driven: UI buttons call `BattleManager.OnRolled()`, `BattleManager.OnActionSelected(int)` and `BattleManager.OnResultButton()`, which forward only if the current state is the right type. The int is cast to `ActionType` (0 Attack, 1 Defense, 2 Magic), so button wiring depends on enum order.

### Data-driven effects (ScriptableObjects)
- `DieFaceSO` — the definition of a face: `faceName`, `description`, `rarity` (`Rarity`), `tags` (`FaceTag`), `baseValue` (starting value of a new copy; upgrades have no cap, `EconomyConfigSO.GetUpgradeCost` is rarity multiplier × current value), `charges` (the Hammer Charge rule), and a list of `ActionEffect { ActionType, EffectSO }`. A face can respond to several actions; choosing an action runs every effect tagged with it.
- `DieFace` — an instance on the die: `definition` + its own `value` + its `enchantment` (or null). Effects use the instance's `value`, and upgrades change only the instance. Never modify a `DieFaceSO` at runtime: two copies on the die share one asset. Always read a face's effects through `DieFace.GetEffects(action)` / `HasAction` (definition effects plus the enchantment's, for Magic), never `definition.effects` directly; show it with `DisplayName` / `FullDescription`.
- `EnchantmentSO` (`Assets/Enchantments/`, renamed from `ActionModuleSO` with its GUID kept) — a Magic action (`effects`, `rarity`, `tags`) inscribed into a `DieFace` whose Magic is empty (`CanEnchant`); one per face. Its effects use the face's battle value. Enchantments can't be removed; replacing the face discards it. They are niche combo tools for high-value faces: judge them with combo tests (`RunSimulator.RunSetup` / `BeforeBattle` put a combo on the die), not by average clear rates.
- Rarity follows value scaling (Common linear, Rare conditional/multi-effect, Epic multiplicative). Design rule: the printed value is exactly what the effects use — no per-effect multipliers (removed on purpose, see DevLog Day 9).
- ScriptableObjects are for design data only. Never store mutable run state in an SO asset: changes made in Play Mode persist in the Editor but not in builds.
- `Effects/EffectSO` — abstract strategy: `Execute(EffectContext context)`. `EffectContext` carries `source`, `target`, `value`, `die` (the source's `List<DieFace>`) and `face` (the triggering `DieFace`). `die` and `face` are null for enemy intents, so effects that read them need a fallback. New information for effects goes into `EffectContext` instead of changing the signature. Every damage effect must hit through `context.Hit(amount)` (adds the source's Rage per hit) and every status applied to the opponent must go through `context.ApplyToTarget(status, amount)` (adds the source's Ritual); self-applied statuses and multiplying an existing status (Fuel) bypass Ritual on purpose. Every effect is source/target-agnostic so the same asset works for the player's die faces and for `EnemyIntent`s. Effects must not reach the die through globals such as `RunManager`.
- `EffectSO.Describe(EffectContext)` returns short player-facing text with the real numbers (Rage, Ritual and current stacks included when the context has a source/target), e.g. "5 damage, 4 Bleed". `EnemyBrain.DescribeCurrentIntent` and the action button previews are built from it, so every new effect should override it.
- Charge (Hammer): `DieCharge` (owned by `BattleFlow`, battle-only) holds temporary value per `DieFace`; `BattleFlow.EndPlayerTurn` resets the acted-with face and gives every other `charges` face +1 (max `DieCharge.MaxCharge`, 5). Effects get the battle value as `context.value` and can read other faces through `context.ValueOf(face)` / `context.charge`; the UI shows it through `UIManager.flow`. `RerollEffectSO` sets `context.rerollRequested`; `BattleFlow.RerollPending` sends `PlayerActionSelectState` back to `PlayerRollState(manager, false)` (no new turn), and the simulator loops the same way.
- `IgniteEffectSO` deals damage equal to the target's Burn without consuming it. `StatusStacksDamageEffectSO` deals damage from a status's stacks without consuming them (target's or own; `addValue` on: value + stacks, e.g. Lacerate; off: stacks, at least value, e.g. Spiked Shield).
- `ConditionalEffectSO` runs its inner effects only if a status is present on the target (or on the source with `checkTarget` off), e.g. "if the enemy is bleeding, hit again". Use it for new "if X" faces instead of writing a new effect class. `ConsumeStatusMultiplyDamageEffectSO` is the multiplicative consume (value × stacks, e.g. Exsanguinate); `ConsumeStatusDamageEffectSO` is the additive one (value + stacks, Detonate).
- `ApplyStatusEffectSO.fixedAmount` (> 0) applies a fixed amount instead of the value (Sword's 1 Bleed).
- `ApplyStatusPerTaggedFaceEffectSO` implements die-composition scaling (value × faces on the die with a tag, e.g. Plague); without a die it counts as 1. New mechanics are added as a new `EffectSO` subclass with `[CreateAssetMenu(menuName = "Dice/Effects/...")]`, not by branching in the states.
- Effect assets and face assets are created in the Editor (`Assets/Faces/` holds the faces). `value` meaning is per effect (e.g. `MultiplyStatusEffectSO` treats it as a multiplier).

### Equipment
- `EquipmentSO` (see GDD "Equipment"): name, rarity, tags and `TriggeredEffect`s (`TriggerType`, optional face-tag / action condition, `EffectSO` list, fixed `value`). `RunData.equipment` holds up to `RunData.EquipmentSlots` (3). Items reuse the normal effect assets; conditions on the battle state use `ConditionalEffectSO`.
- `TriggerSystem` (owned by `BattleFlow`) runs the items. Hits come from `Entity.HitDealt` (raised on the attacker for each hit) and `Entity.HitTaken` (a hit that cost HP; ticks and `PayHP` don't count); every other trigger is fired by a `BattleFlow` step. Effects run by a trigger never fire triggers (no chains). `maxPerRound` / `maxPerBattle` (0 = no limit) cap how often a reaction fires; the limit counts firings even when an inner `ConditionalEffectSO` then does nothing. `TriggerType` is serialized as a number: append only.

### Entities and statuses
- `Entity` holds HP, block and a `Dictionary<StatusType, int>` of statuses (`StatusType` enum is in `Entity.cs`). `TakeDamage` is absorbed by Block first, then Fortify (a status that never resets at turn start), then HP. Damage over time uses `LoseHP` and bypasses both; `PayHP` is the public version for HP costs (e.g. Bloodrage), which can kill the player and is then caught by `CheckBattleOver`. Every state change must raise `OnHealthChanged`, which is how `UIManager` refreshes.
- Block resets at the start of the owner's own turn (`OnTurnStart`), not the end.
- Status rules are hardcoded in `Entity`: Burn deals **no** damage on its own (it is fuel for ignitions and Detonate) and decays by 2 at `OnTurnEnd` unless Burn was added since the last tick; Poison deals its stacks at `OnTurnEnd`, bypassing block, then halves (rounded down); Bleed deals 1 at `OnTurnEnd` and loses 1 stack (stacks are duration); Rage and Ritual are permanent for the battle and are applied by `EffectContext`, not by `Entity`; Vulnerable (+1 per hit taken, in `TakeDamage`), Weak (−1 per hit dealt, in `EffectContext.Hit`) and Entangled (no rerolls, in `BattleFlow.CanReroll`) lose 1 stack at `OnTurnEnd`; FireShield applies Burn to the attacker when hit (only if `TakeDamage` gets a `source`) and is cleared at turn start. Effects that should trigger FireShield must pass `source` to `TakeDamage`.
- Encourage (Ritual's mirror, permanent): every buff an effect gives its own source goes through `EffectContext.GainSelf(status, amount)`, which adds the source's Encourage to Rage, Fortify and FireShield (`IsEncouraged`), never to Block, Ritual or Encourage. `ApplyStatusEffectSO` with `applyToSelf` and `GainStatusPerOpponentStatusEffectSO` (whose `countOwn` counts the source's own buff types, Crowd's Favor) use it. Content carries the Rage + Block tags (see GDD "Encourage").
- Adding a status means touching `StatusType`, `Entity` turn hooks and `UIManager.BuildStatusText` (which lists statuses explicitly).
- Enums used in assets (`StatusType`, `FaceTag`, `Rarity`, `ActionType`) are serialized as numbers: only add new values at the end, never insert or reorder.

### UI
- All canvases use Scale With Screen Size with a 2560x1440 reference (layouts are authored in that space).
- `UIManager` is a Battle-scene singleton (`UIManager.Instance`, cleared in `OnDestroy`); states null-check it before calling `ShowRollPhase` / `ShowRolledFace` / `ShowBattleResult`. It drives the player's `CombatantPanelUI` (name, HP bar, Block/Fortify, status chips), one `EnemyCardUI` per enemy (copied from the inactive `enemyCardTemplate` into `enemyCardRow` by `ShowEnemies`: the enemy's panel, intent, trait chips, a gold TARGET frame and a button that calls `BattleManager.OnEnemyClicked(index)`, which selects the target in the roll and action phases and refreshes the action previews; `RefreshEnemies` runs on every enemy change), the boss die strip (the first enemy's), the rolled face panel, the `DieChipUI`s (on the die net), the `EquipmentChipUI` strip under the player panel (filled by `ShowEquipment`; `BattleManager.Start` subscribes `FlashEquipment` to `TriggerSystem.ItemTriggered` before `StartBattle`, so every item flashes when it fires) and the action buttons, which preview each action from `EffectSO.Describe` (through `UIManager.flow`, so Charge and stone faces show) and are disabled when the rolled face has no effect for that action. References are assigned in the Inspector.
- `UI/GameText` is the single source of keyword colors (`Colorize`) and keyword definitions (`Glossary`, `KeywordTooltip`) for tooltips. Add new statuses/keywords there. `Colorize` wraps keywords that have a definition in TMP `<link>` tags in one pass; a `KeywordLinkTooltip` on a text shows the hovered keyword's definition. The tooltip panel is the `Assets/UI/Tooltip.prefab` (in Battle, Market and RunStart).
- Tooltips: one `TooltipUI` per scene, shown by `TooltipTrigger` components (the trigger object needs a raycast-target Graphic, e.g. a transparent Image).
- Use `ToUpperInvariant`/`ToLowerInvariant` for UI text: on a Turkish system `ToUpper()` turns "i" into "İ".

### Enemy
- Both enemy kinds implement `IEnemyBrain` (`ChooseNextIntent`, `DescribeCurrentIntent`, `ExecuteCurrentIntent`, `OnTurnEnd`, `IncomingDamage`, `ThreatAgainst`, `Traits`, `Die`, `RolledFace`); `BattleFlow` and the simulator only use the interface. Both are plain C# classes created per enemy per battle (`new EnemyBrain(enemySO, self, opponent)`).
- Bosses are `BossSO` assets (`Assets/Bosses/<Name>/`: name, HP, 6 `DieFaceSO` faces with one action each, countdown settings). `BossBrain` (plain C#, `IDisposable`) rolls the boss die at the start of the player's turn as its intent and runs boss mechanics that outlive a turn (the Minotaur's Stampede countdown, started by `StartCountdownEffectSO` through `context.countdownDamage`, staggered by HP lost from hits via `Entity.HitTaken`). `UIManager.ShowBossDie` shows its faces (hidden for normal enemies). `BattleFlow` calls `IEnemyBrain.Bind(flow)` once, so boss effects get the player's die, stone faces and Charge through `EffectContext.targetDie` / `targetPetrification` / `targetCharge`.
- Petrify (Medusa): `Petrification` (owned by `BattleFlow`, battle-only) holds stone faces and their turns left (counted down in `EndPlayerTurn`). A stone face's only action is Defense for `Petrification.StoneBlock` (2) block, handled in `BattleFlow.PlayAction`; use `BattleFlow.CanAct(face, action)` instead of `HasAction` wherever stone matters. `PetrifyHighestFaceEffectSO` petrifies the highest battle-value face for its value in turns; `BossBrain` locks that target (`context.targetFace`) when it rolls the intent, so the telegraphed face is the one that turns to stone. `PetrifiedFacesDamageEffectSO` is Coil (value + bonus per stone face).
- Heads (Hydra): `BossSO.headEnemy` (an `EnemySO`, `Assets/Bosses/Hydra/HydraHead.asset`) turns on the heads rules in `BossBrain`. Each head is a separate `BattleEnemy` spawned through `BattleFlow.SpawnEnemy` (`startingHeads` in `Bind`, behind the body). A dead head counts as cut (`CutHeads`); at the start of the body's turn (`ExecuteCurrentIntent`) each cut head grows back as two, reviving dead heads first (`Entity.Revive`, `EnemyBrain.ClearIntent`, so they act from the next turn) and spawning new ones up to `maxHeads` alive, unless the body has a `regrowthBlockedBy` status (Burn: the cut is settled without growing). The body heals `regenPerHead` per living head in `OnTurnEnd` unless it has a `regenBlockedBy` status (Burn, Bleed). A boss is created with `endsBattleOnDeath`, so the battle ends when the body dies. `HealUnlessStatusEffectSO` is Regrow. Bots go for the body unless Burn blocks regrowth (`RunSimulator.HydraFocusBody` switches this off for comparisons); `RunSimulator.DeathRateAt(battle, bots, runs)` measures a battle's kill rate among the runs that reach it.
- Enemy traits (see GDD "Enemy Traits"): `EnemySO.traits` lists `EnemyTrait`s (`EnemyTrigger`: `Passive`, `HitByPlayer`, `LostHPFromHit`, `PlayerChoseAction`, `PlayerRerolled`; optional action / `requireBlock` / `requireTargeted` (only when this enemy is the player's target, e.g. Parry) / `requireUnblocked` (the hit lost nothing to Block or Fortify, `Entity.LastHitAbsorbed`) conditions, `nextTurn` (the effects wait for the start of the enemy's next turn, after its Block reset, run by `BattleFlow.EnemyAct` through `EnemyTraitSystem.RunPending`, and the card shows them while waiting; Curl Up), `maxPerBattle`, effects run with the enemy as source and the player as target). `EnemyTraitSystem` (one per `BattleEnemy`, created by `BattleFlow`, fed by `IEnemyBrain.Traits`; bosses have none) runs them, the equipment trigger idea from the enemy's side; effects run by a trait never fire traits. `RetaliateDamageEffectSO` is Thorns/Parry damage (no Rage, no source). Threat intents use `PunishChoiceEffectSO` (hits on the enemy's turn only if the player's last action, `BattleFlow.LastActedFace` / `LastActedValue` / `LastAction` passed as `context.targetLastFace` etc., met its condition: a face below a value threshold, `DieFaceSO.hasNoValue` counting as below, or a chosen action); they don't count in `IncomingDamage`, `IEnemyBrain.ThreatAgainst(face, value, action)` reports them, and bots reroll or switch actions to dodge them. Second Wind is `EnemySO.secondWindIntents`, which `EnemyBrain` switches to below half HP. Traits show as chips on the enemy's card (`EnemyCardUI`), flashing when they fire. `EnemyTrigger` is serialized as a number: append only.
- Normal enemies are `EnemySO` assets in `Assets/Enemies/` (name, `EnemyTier` Weak/Medium/Strong, HP, `escalationPerTurn`, intents). `EncounterConfigSO` (`Assets/Config/EncounterConfig.asset`) lists every enemy; the battle scene has a single generic Enemy object whose `Entity` stats are set from the picked boss or the encounter's first member in `BattleManager.Awake` (copies of it hold the other members, named "Tiro A" / "Tiro B" by `BattleManager.MemberNames`), which creates each `EnemyBrain`.
- Difficulty curve: `EncounterConfigSO.battleScaling` lists `BattleScaling { battle, hpMultiplier, startingRage }` for normal enemies (`ScalingFor`, `ScaledHP`); `BattleManager.Awake` and the simulator's `FightBattle` apply it (HP and a starting Rage status), and the Market preview shows it. Bosses aren't scaled. The simulator reports "avg HP lost by battle" (the fight only) to tune it.
- Enemy groups: `EncounterConfigSO.groups` lists `EnemyGroup`s (name, tier, up to 3 `members` in turn order, `hpMultiplier` applied to each member's maxHP by `MemberHP`). `EncounterConfigSO.PickEncounter(enemies, groups, tier, met)` picks a lone enemy (`EnemyGroup.Alone`) or a group, every candidate equally likely, never anything with a met member until the tier runs out, and marks the members met; `RunManager.PickEncounterForNextBattle` and the simulator both use it. `RunSimulator.ForceEncounter` (null by default) lets experiments fight a chosen encounter at a tier, e.g. to compare a group's HP taken and loss rate with the lone enemies' through `FightStats`.
- `EnemyIntent { intentName, intentType, effects, value, weight }`: all effects run with the same value. `EnemyBrain` stores both entities; it picks intents by weight at the start of the player's turn (the same intent at most 2 times in a row), shows them via `DescribeCurrentIntent`, and runs them in `EnemyTurnState` through `ExecuteCurrentIntent()` (with no `die`/`face` in the context).
- Escalation uses the shared, visible Rage status: intents like Battle Cry or Roar use `GainRageSelfEffect`. `EnemySO.escalationPerTurn` (Rage gained in `EnemyBrain.OnTurnEnd()`) still works but no enemy uses it (Essedarius's made slow builds unwinnable, DevLog Day 33). There is no hidden enemy attack bonus anymore.
- Balance experiments: `RunSimulator.WithFaceValueChanges(deltas, measure)` changes faces' base value in memory and always restores them; `ClearRates(bots, runs)` and `BotsMatching(...)` keep experiment code short (the MCP `execute_code` compiler is C# 6, so avoid generic inference tricks). Reports include gold entering the first Grand Market and the average die at battle 8. For deeper diagnosis set `RunSimulator.Stats = new RunSimulator.FightStats()` (optionally its `statsTier`), run `Simulate`, read `Stats.Report()` (damage per player turn from actions vs. ticks, HP taken, Bleed uptime, damage per roll for each face) and set it back to null.
- Balance is tuned with `Assets/Editor/RunSimulator.cs` (menu `Tools → Gladiator Dice → Run Balance Simulation`, or call `RunSimulator.DefaultReport(runs, hpScale, damageScale)` from MCP `execute_code`). It simulates full runs with the real `Entity`/`EnemyBrain`/effects/`Market` and its bots (no shopping, unplanned, opportunist, one focused bot per archetype tag, and hybrid bots with several tags: Ritual + Poison, Ritual + Bleed, Block + Rage, Bleed + Rage; `ChooseAction` has face-specific rules that new faces may need), without scenes. The bots map to GDD "Every Run Is Its Own Build": the unplanned buyer is a bad-decisions run, the opportunist (`ShopOpportunist`: its focus is the two most common tags beyond the starting die, it takes Rare or Epic opportunities and never pays to reroll) a normal run, and a focused bot's report line "clear rate by build faces at battle 8" shows how much a complete build pays. Focused bots reroll the Market when nothing fits and they keep at least `GoldToKeepAfterReroll` (40) gold, and spend gold left after upgrades on enchantments of their archetype, inscribed onto faces outside it (`BuyEnchantments` switches this off for comparisons; `PlayEnchantments` off buys them but never plays them, to separate their gold cost from their use). Bots only buy Epic enchantments (Common ones are sidegrades that made bots stop hitting); they go on the highest-value face (Charge faces count +3) and have per-enchantment play rules in `PlaysEnchantment`. They also take the boss reward and buy equipment they want (`Bot.Want`: archetype 2, general 1, other 0; `UseEquipment` switches it off). Its fights use the same `BattleFlow` steps as the states and fight bosses in their slots (`EnemyTier.Boss` labels them in `FightStats`); its reward rules mirror `RunManager.OnBattleEnded`, so keep those in sync when they change. Scale arguments only affect simulation copies of the enemies.
- The next battle is picked ahead: `RunManager.GoToMarket` calls `PickNextBattle` (`RunData.nextBattlePicked` / `nextBoss` / `nextEncounter`), `MarketUI.ShowNextBattle` shows it, and `BattleManager.Awake` takes it with `TakeNextBattle` (which picks if nothing was picked, e.g. the first battle).
- `RunManager.PickEncounterForNextBattle` picks by tier (`GetTierForBattle`: Weak before the first boss slot, Medium from it, Strong from the second; boss slots use the next tier until bosses exist) and never repeats an enemy within a run (`RunData.metEnemies`, which group members count toward).
